# huawei_solar 2.0.15.4 — Release Audit

**Scope:** A genuinely new, deliberately simple experiment — broadband random excitation. The three prior releases in this line (2.0.15/2.0.15b/2.0.15.3) all shared the same underlying design: sequential, long-dwell (4h minimum) levels, one lever at a time, letting the channel settle before each measurement counts. That design has a structural blind spot it can never close by construction: it cannot observe what happens in the minutes immediately after a parameter changes, while the channel still carries residual state from whatever came before — and it can never observe joint interaction between GAP, TIMEOUT, and POLL, since only one lever ever varies at a time.

This release exists specifically to close that blind spot. Every 10 minutes, GAP, TIMEOUT, and POLL are redrawn independently and uniformly at random within their own already-validated bounds. No go/no-go safety monitor. No persistence across restarts. Confirmed explicitly with the person who commissioned this release before any code was written: this is read-only telemetry collection, so an unstable channel under this mode degrades data collection, not physical inverter safety — and the edge-transition instability this mode may produce is exactly the data the real controller (built later, on 2.0.14) needs to be designed to avoid.

**Final verification:** 1,387 passed, 1 skipped — confirmed identically from a fresh, independent extraction of `huawei_solar-2.0.15.4.zip`, matching the established pre-existing baseline (5 failed / 12 errored, documented since 2.0.7) with zero new regressions. 1,387 = 1,358 (2.0.15.3 baseline) + 29 new tests.

---

## Design, confirmed directly before writing any code

- **No code-level coupling between `poll_interval` and `request_timeout` exists anywhere in this integration** — checked directly across `adaptive_modbus.py`, `update_coordinator.py`, and `modbus_guard.py` before this release was designed, in response to a direct question about whether one was assumed. All three levers (GAP, TIMEOUT, POLL) are drawn fully independently.
- **All three ranges confirmed within this project's own already-validated hard bounds** (`const.py`'s `ADAPTIVE_GAP_MIN/MAX`, `ADAPTIVE_TIMEOUT_MIN/MAX`, `ADAPTIVE_POLL_MIN/MAX`) before implementation began. TIMEOUT's own floor (30s, not the full 15s `ADAPTIVE_TIMEOUT_MIN`) matches the 30s floor already agreed for the sequential excitation releases, for the same reason: several register classes were found to need timeout ≥25-35s to avoid spurious timeouts, and this release has no reason to risk reproducing that already-fixed regression just because it draws randomly rather than sequentially.
- **Shared per bus endpoint**, reusing the exact `get_or_create(bus_endpoint)` registry pattern `ExcitationController`/`ModbusGuard` already established — for the same reason 2.0.15.3 needed it: GAP is combined across every device on a bus via `ModbusGuard`'s own `max()`, so independent per-device draws would silently produce an effective GAP governed by whichever device happened to draw the larger value, not a controlled observation of either draw.
- **`max_queue_depth` deliberately untouched** — outside this release's own randomization scope, per direct confirmation.
- **Deliberately no go/no-go monitor and no persistence** — both omissions are architectural choices specific to this release's own purpose, not gaps left over from the sequential design. See `random_excitation_controller.py`'s own module docstring for the full reasoning on each.

## Real bugs found and fixed during implementation, before delivery

Three were caught during construction, all before any test was run:
1. A stray, unused deferred-import pattern mistakenly applied to `dataclasses.replace` (a standard-library function with no circular-import risk at all) — a leftover mental shortcut from the pattern legitimately needed elsewhere for `AdaptiveParams`. Caught on re-read, removed.
2. A `NameError`-causing undefined variable (`REDRAW_INTERVAL_LOG_STR`) referenced in a log message. Caught by the compile check, fixed by importing the real constant instead.
3. **The most consequential one**: a device upgraded in place from 2.0.15.3, without clearing storage, would have silently restored the *old* sequential `ExcitationController` from leftover persisted data — giving this release the wrong excitation mechanism for the rest of the session, with zero warning. This is exactly the class of silent, field-discovered surprise this project has already spent real effort tracking down more than once. Fixed by explicitly recognizing legacy `"excitation"` keys in storage and discarding them with a clear log message, rather than attempting to restore them.

A fourth issue was caught proactively, not reactively this time: the sensor-list-drift bug found earlier this session (a rename in `snapshot()` not propagated to `_ADAPTIVE_SENSORS`, discovered only via a live screenshot) was checked for directly before shipping, rather than waiting to be reported again. `RandomExcitationController.telemetry_snapshot()` uses deliberately disjoint key names (`random_excitation_*`, not `excitation_*`) from `ExcitationController`'s own, confirmed directly, and both sets of sensor entries now coexist permanently in `_ADAPTIVE_SENSORS` — each showing "Unknown" precisely when its own excitation class isn't the one currently active, which is correct, accurate absence, not a bug.

## Integration into `AdaptiveModbusController`

`enable_excitation()` now instantiates `RandomExcitationController` for this release, not `ExcitationController` — confirmed with the person commissioning this release that a single toggle replacing the mechanism outright, rather than a second, parallel option, matches the explicit "keep it simple, this is throwaway experimental code" instruction. `excitation_is_halted()` now always returns `False` and `resume_excitation_after_halt()` is now an unconditional no-op — both kept as real, callable methods (not removed) so `button.py`'s existing `ResumeExcitationAfterHaltButtonEntity` continues to work unchanged against this release: pressing it correctly does nothing, since nothing can ever be halted, rather than the entity needing its own release-specific special-casing.

## Existing tests updated to reflect genuinely changed behavior, not routed around

13 test failures surfaced on the first full-suite run after wiring this in — all traced to tests that called `AdaptiveModbusController.enable_excitation()` and then asserted `ExcitationController`-specific behavior (halt states, `excitation_mode` telemetry fields) that this release's own `enable_excitation()` no longer produces. Each was individually examined, not batch-deleted:
- Tests verifying `ExcitationController`'s own shared-registry and telemetry behavior were rewritten to construct that class directly, since the class itself is unaffected by which one `enable_excitation()` happens to wire up for a given release — the class still exists, still works, and is still tested on its own merits.
- The two button tests asserting a press *genuinely resumes* a halt were rewritten to instead confirm the actual, correct behavior for this release: a press is always a safe no-op, even against a manually-constructed, halted-looking `ExcitationController`, because `resume_excitation_after_halt()` is now unconditional — verified directly that the original test's own premise no longer holds, not just assumed.
- The sensor-key-correspondence tests were updated to be excitation-class-aware, correctly excluding the legacy `excitation_*` keys (or the new `random_excitation_*` keys, in the base-case test) from the "must be present" check, rather than requiring every key from every excitation generation to coexist simultaneously.

## Testing

29 new tests, real execution throughout, in `test_random_excitation_controller.py`:
- **Draw bounds** (`TestRandomDrawBounds`): 500-sample statistical check that every draw stays within bounds (not a single lucky sample), the exact bound values pinned against `const.py`'s own hard bounds, and an adversarial check that the three levers are not secretly coupled.
- **Shared registry and `apply()`** (`TestSharedRegistryAndApply`): same-endpoint reuse, different-endpoint isolation, two devices sharing a bus applying identical values, `max_queue_depth`/`confidence` left genuinely untouched, `in_transition` always overriding.
- **Redraw timing** (`TestRedrawTiming`): no redraw before the interval elapses, redraw happens once it has, the clock resets, and repeated calls before the interval is harmless (matching real multi-device polling behavior).
- **No go/no-go monitor** (`TestNoGoNoGoMonitor`): `record_outcome()` never raises regardless of outcome, 500 recorded failures never change `apply()`'s own behavior, and — adversarial — no `_state`/`_gonogo`/`_halt_reason` attribute exists on the class at all, not just "always returns False" logic hiding an unused one.
- **No persistence** (`TestNoPersistence`): neither `to_persisted_dict()` nor `from_persisted_dict()`/`get_or_restore()` exist on this class.
- **Telemetry snapshot** (`TestTelemetrySnapshot`): reflects the current draw, applied values correctly `None` before any `apply()` call and correctly `None` again during a transition override (not a stale prior value).
- **Full `AdaptiveModbusController` integration** (`TestAdaptiveModbusControllerIntegration`): `enable_excitation()` genuinely instantiates the right class, two devices on a shared bus get identical real params through the real `get_params()` path, learning disables/re-enables correctly, 200 recorded failures through the real `record_request()` path never halt anything, `_serialize()` never includes an `"excitation"` key, and — the real, end-to-end version of the most important fix in this release — legacy 2.0.15.3 persisted excitation data is confirmed discarded, not restored, through the actual `_deserialize()` path.

## Post-delivery correction — TIMEOUT floor lowered from 30s to 20s, no version bump (not yet deployed)

Before deployment, the TIMEOUT lower bound was reconsidered and changed from 30s to 20s, following a direct discussion of this release's own actual purpose. The original 30s floor (matching the sequential releases) existed to avoid reproducing an already-fixed regression — several register classes need timeout ≥25-35s to avoid spurious timeouts. That reasoning is correct for releases producing clean envelope data, but this release exists specifically to generate evidence for designing the real filter/coordinator — which needs to correctly handle exactly the edge conditions production should avoid, not just data that stays clear of them. Confirmed directly: a spurious timeout here means an abandoned, retried read (this is read-only telemetry collection, no physical safety implication), and the resulting data directly characterizes the real transition each register class hits, rather than only inheriting simulation-derived estimates never confirmed against genuinely independent, randomly-sampled conditions.

**GAP was deliberately NOT lowered the same way**, after checking `modbus_guard.py` directly rather than assuming the same logic applied: `MIN_INTER_REQUEST_GAP` (150ms) is documented as a hardware constraint (SUN2000 Modbus FSM reset time ≈100ms), already tested lower (30ms) and found to cause "pervasive 0x06 SLAVE_DEVICE_BUSY responses on all SUN2000 hardware" — a known, uniform failure mode already characterized once, not an open boundary worth re-discovering. The guard also clamps to this floor unconditionally regardless of what this module draws, so lowering `GAP_MIN_MS` below 150 would have been silently ineffective on the real wire in addition to being unadvisable — confirmed directly in the guard's own code before this distinction was drawn, not assumed.

Re-verified after the change: 2,000 real draws confirmed all correctly within the new [20, 60]s range; full suite re-run at 1,387 passed, same known baseline, zero regressions; re-packaged and independently re-verified from a fresh extraction below.

## What comes next

Deploy for the planned 3-day run, alongside 2.0.15.3 continuing to run for two more days as already agreed — no time pressure drove this implementation. `random_excitation_draw_*` fields are now visible both in telemetry and as live diagnostic sensors, matching the visibility standard established for the sequential releases. Per the standing agreement across this entire 2.0.15.x line: this release exists to generate evidence, not to become the thing that ships — the real implementation is built later, on 2.0.14, carrying forward only the specific, independent fixes discovered along the way, deliberately, not the experimental scaffolding itself.
